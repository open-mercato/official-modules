# Lessons

- 2026-07-08 · financial_pl: a "block edits of submitted X" guard must cover every writer of the record — the command's undo (both create- and update-op) and the transient claim status ('submitting') too, or the same falsified-compliance-record hole survives through the other doors → guard on submitted OR submitting in execute AND undo.
- 2026-08-14 · financial_pl (invoice CrudForm): CrudForm re-seeds ALL its fields when `crudInitialValues` changes identity (skipping only user-edited ones). So (a) writing a *whitelisted* header field like currency from an async settings effect RESETS other header/derived-date fields to mount defaults — seed pre-mount or guard on untouched-only; (b) a saved `metadata.*` field reads back only if its key is added to the `crudInitialValues` whitelist, not merely to the page's `header` mapping.
- 2026-08-14 · financial_pl (lists): financial_pl invoices never set core `sales_invoice.status` (issuance state lives in `KsefSubmission`), so a list filter doing exact-equality on that column always returns 0. Derive document status from `KsefSubmission` (accepted/offline_issued) as an `id` `$in`/`$nin` complete partition, resolving the accepted-id set scoped, and intersect positive sets in JS (don't rely on two `$in` under one key).
- 2026-08-14 · financial_pl (KSeF creds): an integration `type:'secret'` field (KSeF auth token) DOES save via core's encrypted credentials path — a "not configured" symptom is usually the *certificate*-specific 409 on the certs page (a token can't satisfy it), not a failed token save. The real latent bug: the module READS credentials by the selected-org cookie (`resolveOrganizationScopeForRequest`) while core WRITES by active-org (`resolveActiveOrganizationId`) → super-admin split-brain; fix by scoping the write like the module reads, never by switching reads to auth.orgId.
